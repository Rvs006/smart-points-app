Electracom Smart Point Reference Product Brief
The basics

What this tool is, and the idea it’s built on.

A one-minute orientation for anyone new to the product or the vocabulary it uses. Everything else follows from these few ideas.

In one sentence

A single-page tool for naming the thousands of data points in a building’s management system consistently across every project — using a shared, published vocabulary so data travels cleanly between jobs.

Why a tool for this exists

Every building project creates thousands of data points — temperatures, pressures, on/off statuses, setpoints — all exposed by the Building Management System. If every project names those points differently, the data becomes a mess: it can’t be reused on the next job, can’t be compared across buildings, and every handover requires a translator.

A shared vocabulary — not vendor-specific, not project-specific — solves that problem. This tool is how the shared vocabulary becomes usable day-to-day: searchable, buildable, checkable, exportable.

The ontology in 90 seconds

The vocabulary is DBO, Google’s Digital Buildings Ontology. Two ideas are enough to start:

🧱
Subfield
One small approved word — supply, air, temperature, sensor. Each belongs to one category: descriptor, component, measurement, point type.
🏛️
Field
A finished name, built by joining subfields in the correct order with underscores. supply_air_temperature_sensor is four subfields clicked together.

A worked example

Here’s a typical name being assembled from subfields — descriptor first, then component, then measurement, then point type. The finished string is what ends up in the BMS.

Descriptorsupply
Componentair
Measurementtemperature
Point Typesensor
↓
supply_air_temperature_sensor

Every subfield in the finished name must be a recognised DBO term. The tool checks this on every name you build, import, or submit — and spells out which subfield is off when something fails.

Key features

Everything the app does, grouped by capability.

A map of what the product offers. Each card describes a capability. The guided tour in the next tab shows these in action, through the eyes of each role.

📚
Full Point Library
Every data point the app knows about, tabbed by system (BMS, power, fire, access, lifts, lighting, CCTV).
  • Full-text search across names, descriptions, projects
  • Two-column compliance view: exact DBO + structural
  • Sort, filter, and export any slice
🏗️
By-Equipment View
Same points, grouped under equipment. Per-asset detail with gap analysis.
  • Variants roll up into one canonical entry
  • Subtype pill bar inside each detail panel
  • Per-asset export as a checklist
🗃️
Subtype Catalogue
Dedicated workspace for subtype-level records: manufacturer, model, notes, plus suggested mappings.
  • One record per asset + subtype
  • Manufacturer / model / notes fields (admin-edit)
  • Required / Optional / Observed extras view
🧩
Name Builder
Structured form for assembling an ontology-compliant name. Seven ordered subfield slots.
  • Dropdowns scoped to each subfield category
  • Repeatable descriptor slots
  • Live validation as the name assembles
🛡️
Validation
Single errors table covering every custom-added point — structural, vocabulary, and semantic checks all in one place.
  • Uniform error severity
  • Suggested fixes alongside each error
  • Live feedback inside Builder and Submit
📥
Submit & Review
Lightweight proposal workflow. Non-admins propose; admins approve, reject, or request changes.
  • Live validation under DBO name field
  • Approve/reject gated behind sign-in
  • Approved submissions land in main library
🧮
Tender Sizing
Calculator taking equipment quantities → estimated total point count. Typical and Max sizing modes keep the output honest.
  • Typical mode: realistic single-install count
  • Max mode: worst-case union across projects
  • Mode is saved and exported with the estimate
🔐
Sign-In & Admin Gating
Administrative actions sit behind an admin sign-in. Non-admin users see views without edit controls.
  • First visit creates an admin account
  • Sessions expire after inactivity
  • Admin buttons hidden when signed out
🔄
Ontology Sync
Published vocabulary can evolve. The app pulls the latest on demand or weekly, reporting the diff.
  • Sync status pill in nav: “fresh” / “N days ago”
  • Manual or weekly auto-sync
  • Each sync reports the diff
📤
Export & Import
Three formats — CSV, Excel, JSON — all using a shared canonical schema so files round-trip cleanly.
  • Filtered exports include _filtered in filename
  • Imports (admin-only) from JSON or CSV
  • Excel workbook has ontology reference sheet

Section reference

What each section is for.

A card per section. Description, capabilities, a gotcha box, and a “try it yourself” prompt so you can ground the reference in the actual app.

Point Library
for everyone

Master list of every point, tabbed by system. First stop when you want to know whether a point already exists.

What it does well
  • Full-text search across names, descriptions, projects
  • Filter by system, asset, DBO status, compliance
  • Two-column compliance view: exact + structural
  • Sortable, searchable, exportable
⚠️
Two compliance columns, two questions

“In DBO” ticks when the exact combined name is on the published list. “Structurally compliant” ticks when every underscore-separated subfield is valid, even if the combined name isn’t published.

Try it yourself

Open Point Library, pick BMS / MEP, sort by “In DBO”. Scroll to see custom-but-compliant points.

By Equipment
for everyone

Same points, grouped under equipment. Per-asset detail with gap analysis.

What it does well
  • Canonicalisation — aliases collapse to one bucket
  • Subtype drill-down pills
  • Coverage summary: captured vs standard
  • Per-asset export as checklist
Try it yourself

Click AHU, then AHU TYPE-1 pill. The count changes — smaller is realistic per-install; larger is the union.

Subtype Catalogue
edit = admin only

Standalone workspace with manufacturer / model / notes metadata plus suggested point mappings.

What it does well
  • One record per asset + subtype
  • Asset filter, free-text search
  • Required / Optional / Observed extras mappings
  • One-click handoff to By Equipment
⚠️
Mappings are suggestions

Required/optional/observed is computed from the standard baseline + project data. Treat as a starting point, not an authoritative list.

Try it yourself

Filter asset to FCU, click any subtype, look at Observed Extras — points seen on real projects but not on the standard baseline.

Name Builder
for everyone

Structured form for assembling an ontology-compliant name. Seven ordered slots snap together with underscores.

What it does well
  • Descriptor slots repeat for compound chains
  • Live validation as name assembles
  • Slot order enforced
  • Free-text and structured validate identically
💡
Order matters

Two names with the same subfields in different order are not equivalent. The builder enforces the correct order.

Try it yourself

Build return_air_temperature_sensor using dropdowns. Add outside to see it become outside_return_air_temperature_sensor.

Validation
for everyone

Bulk view running every check against every custom-added point. One errors table.

What’s checked
  • Structural: lowercase, underscores, no leading digit
  • Semantic: ends in a known point type; _status on analogue flagged
  • Vocabulary: every subfield in ontology
Try it yourself

Open Validation. Each row names the offending point and spells out which rule it broke — no decoding needed.

DBO Lookup
for everyone

Two-column reference browser: full field names left, subfields right. Each with category and description.

Try it yourself

Type humidity in subfield search — see its category (measurement) and description. Then search fields for the same word — every published compound using it.

Submit / Review
dual-mode

Proposal workflow. Non-admins submit; admins approve or reject. Approved submissions land in the main library.

⚠️
One queue per browser

The pending queue lives in browser local storage. A submission on one machine won’t appear on another until a shared back-end exists.

Try it yourself

Signed out, type supply-air-temp-sensor in the submit form. The live panel highlights three issues before you even click Submit.

Tender Calculator
for everyone

Enter equipment quantities → estimated total point count with optional cost.

Typical vs Max
🎯
Typical

Max distinct points on any single project. Realistic per-install count. The default.

⚠
Max

Union of all distinct points across every project. Worst-case envelope.

Try it yourself

Enter 3 AHUs, flip between Typical and Max. Numbers differ noticeably — Typical is usually 25-40% of Max.

Projects
for everyone

Per-project comparison. See which points each project carried, side by side.

Try it yourself

Click a project card. The “Projects” column on each row shows which other jobs used the point.

Entity Types
reference

Ontology-browser for entity types — equipment families with their standard point set. Authoritative reference for “what points ought this equipment have?”

Try it yourself

Filter by namespace, click AHU. Required and optional lists are the baseline every AHU on every project is measured against.

Connections
reference

How entities connect in the ontology, plus published units reference and spatial hierarchy (site → building → floor → zone).

Try it yourself

Scan the connection types list — each is a verb-like relation between two entities, the shape of “what talks to what” in any building.
