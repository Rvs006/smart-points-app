01

What this tool actually does

Before the buttons and the code — why does the Smart Point Reference exist, and what problem does it quietly solve every day?

1.1The problem, in one sentence

Every BMS project creates thousands of data points — temperatures, pressures, on/off statuses, setpoints. If every project names them differently, the data becomes a mess that can't be re-used, compared, or handed over cleanly.

🎯
The job of this tool

Make it easy for Electracom's MSI team — and eventually the whole business — to name BMS points the same way across every project, in line with Google's Digital Buildings Ontology (DBO).

1.2A metaphor: the dictionary for a new language

Imagine every country invented its own word for "temperature." Every thermometer ever made would have to ship with a translator. That is what BMS naming was like before DBO — every vendor, every project, every engineer had their own style.

DBO is the shared dictionary. The Smart Point Reference tool is the thesaurus sitting next to it — it helps you pick the right word, build compound words correctly, and flag when someone has invented a word that isn't in the dictionary yet.

📚

DBO

Google's published vocabulary. Thousands of approved field and subfield names. Updated over time.

🔖

The tool

Lets engineers search, browse, build and validate names without having to memorise the whole dictionary.

🏗️

The project

Minerva House, 334 Oxford Street, every future job — all using the same names means data travels between jobs cleanly.

1.3What lives inside the tool today

DBO in plain English

The ontology that underpins every point name in the tool. No jargon, no hand-waving — just what it is, and why it matters.

2.1Subfields are Lego bricks

DBO is not just a list of point names. It's a list of building blocks — called subfields — that you snap together to make a full name.

A point like supply_air_temperature_sensor is not one word DBO shipped with. It's four Lego bricks: supply, air, temperature, and sensor. Each brick is in DBO's approved list. Clipped together with underscores, they form a legitimate point name that any other DBO-aware tool can read.

Descriptorsupply
Componentair
Measurementtemperature
Point typesensor
supply_air_temperature_sensor

2.2Fields vs subfields — what's the difference?

🧱

Subfield

One individual brick. supply, air, discharge, sensor, setpoint, pressure. Each lives in one category (descriptor, component, measurement, point type, etc.).

🏛️

Field

A finished, approved combination. supply_air_temperature_sensor exists as a recognised DBO field. Many subfield combinations don't exist as named fields — and that's fine, as long as every brick is valid.

💡
Key insight

The tool cares about structural compliance (every brick is a real brick) more than field-level compliance (this exact combination is published). Real projects constantly invent new brick combinations for edge cases — that's normal and allowed.

2.3How the tool stores this

Inside the tool, DBO lives in two simple lists: D.f (every approved field name) and D.sf (every approved subfield with its category). Both are refreshed by the "Sync DBO" button — more on that in Module 7.

Here's the compliance check the tool runs on every point name:

the data lists 
function isCompliantName(nm){
 if(!nm)return 0;
 var segs=String(nm).split('_').filter(Boolean);
 if(!segs.length)return 0;
 for(var s=0;s<segs.length;s++)
  if(!sfSet.has(segs[s]))return 0;
 return 1;
}
Plain English

Given a point name, is every brick in it a recognised DBO brick?

If the name is empty, it can't be compliant. Return "no".

Split the name on underscores to get the individual bricks. supply_air_temperature_sensor becomes [supply, air, temperature, sensor].

If there are no bricks at all, return "no".

Walk through every brick. If any one of them isn't in the approved DBO subfield set, return "no" — even one unknown brick fails the whole name.

If we got through all of them, the name is structurally compliant. Return "yes".

🔎
What "compliant" means here

This is the Compliant column you see in the Point Library. It's the stricter check. The separate In DBO column is a looser check — just whether the exact field name is on Google's published list.

3.2The asset-collapsing trick

Old project data is messy. The same AHU might be called "AHU TYPE-1" on Minerva House, "AHU TYPE-2" on Oxford Street, and "Air Handling Unit" on an older job. If the tool treated those as three different things, the By Equipment view would be nonsense.

The tool handles this with a small list of regular-expression rules — one entry per equipment family — that collapse every variant into a single canonical name. The original name is kept as the subtype so nothing is lost.

canonicalisation rules 
var ASSET_NORM=[
 {re:/^AHU(\s|$|TYPE)/i,canon:'AHU'},
 {re:/^Air Handling Unit/i,canon:'AHU'},
 {re:/^FCU(\s|$|TYPE)/i,canon:'FCU'},
 {re:/^Fan Coil/i,canon:'FCU'},
 {re:/^VAV(\s|$|TYPE|EXT|SUP)/i,canon:'VAV'},
 {re:/^ACU(\s|$|TYPE)/i,canon:'ACU'},
 {re:/^FAN (EF|SF|SEF)/i,canon:'Fan'},
 {re:/^PMP /i,canon:'Pump'},
];
Plain English

A rulebook, read top-to-bottom. The first matching rule wins.

Rule 1: anything that starts with "AHU" followed by a space, end of string, or the word "TYPE" → call it AHU.

Rule 2: anything starting with "Air Handling Unit" → also AHU. So "AHU TYPE-1", "AHU", and "Air Handling Unit" all land in the same bucket.

Same pattern for Fan Coil Units (FCU), Variable Air Volume boxes (VAV), Air Cooling Units (ACU).

For fans, only prefixes like "FAN EF" (extract fan), "FAN SF" (supply fan), "FAN SEF" count — so a random "FAN MOTOR SPEED" isn't mistakenly collapsed.

Pumps are matched on the abbreviation "PMP " (with a space) or the whole word "Pump".

The Name Builder

Seven slots that snap together into a DBO-compliant name. This is how a design engineer proposes a new point without having to memorise the ontology.

4.1An assembly line for names

DBO names are not arbitrary. Subfields must go in a specific order, and each slot draws from a specific category. The Builder section is essentially a filling-in-the-form tool for that order.

Metaphor: think of it as a conveyor belt with seven stations. Each station has a tray of parts (the subfields in that category). You drop a part onto the belt as it passes. At the end, the parts are welded together with underscores into one finished name.

Agg. Desc—
Descriptor(s)supply
Componentair
Meas. Desc—
Measurementtemperature
Point Typesensor
supply_air_temperature_sensor

4.2Why slot order matters

Two DBO names with the same subfields in a different order are not equivalent. supply_air_temperature_sensor and temperature_air_supply_sensor are not the same thing as far as any downstream tool is concerned.

Aggregation and aggregation-descriptor go at the start, not at the end — matching the real DBO spec. Here's the code that glues the slots together in the right order:

name-builder slot order 
function bld(){
 var descs=(S.bds||[]).filter(Boolean);
 var parts=[S.bag,S.bagd].filter(Boolean)
   .concat(descs)
   .concat([S.bc,S.bmd,S.bm,S.bp].filter(Boolean));
 return parts.join('_');
}
Plain English

Start with any descriptor slots the user filled in, skipping empties. Descriptors are the only slot you can have more than one of — think "supply" and "mixed" on the same air stream.

Now line them up in strict order: aggregation first, then aggregation-descriptor, then the descriptor(s), then component, then measurement-descriptor, then measurement, then point-type.

Drop any slot that's empty — not every point needs all seven.

Glue the surviving slots together with underscores. That's your finished name.

4.3The seven slots, with examples

aggregationA rolling-up concept. Example: average, max. Rare — usually empty.
aggregation_descriptorQualifies the aggregation. Also rare. Keeps DBO compatible with very specific analytics.
descriptorWhere the thing is, or what kind it is. supply, return, zone, outside. Can repeat.
componentThe physical stuff: air, water, fluid, steam, gas.
measurement_descriptorQualifies the measurement. relative (humidity), differential (pressure).
measurementWhat's being measured: temperature, pressure, flowrate, humidity.
point_typeThe kind of data point. sensor, setpoint, command, status, alarm. Required — every name must end with one.

4.4Why one slot — the descriptor — can repeat

A real example from the HVAC world: supply_air_temperature_sensor on an AHU has one descriptor (supply). But if you're measuring temperature on the mixed air stream that comes before the supply fan, you might want mixed_supply_air_temperature_sensor — two descriptors, stacked.

The Builder allows the descriptor slot to repeat so chains like mixed_supply_air_… are expressible without dropping to free-text.

➕
In the UI

Look for the "+" button next to the descriptor slot in the Builder. Each click adds another descriptor that joins the chain.

4.5Free-text vs dropdowns

The Builder has two modes. The dropdowns are the structured path — pick a subfield, pick another, watch the name assemble. The free-text box lets experienced users type a whole name directly; validation runs the same way on either path.

When should you use which?

Validation — the rules behind the errors

The invisible layer that catches typos, bad suffixes, and made-up vocabulary before they poison a project.

5.1Spell-check for a new vocabulary

If the Name Builder is a word-processor, validation is the red squiggly underline. It runs on every name the tool sees — in the Library, in the Builder, in the Submit form — and surfaces anything that breaks the DBO rules.

The tool takes a strict position on validation: only flag things where the point subfields are incorrect. Every single validation issue is an error — if the tool flags something, it's a problem that needs fixing, not a gentle suggestion.

🎯
What this look like in practice

Grep for sev:'warning' or sev:'info' in the current code returns zero hits. The validation output has one severity: error. That means anything on the error list is real work — not noise to skim past.

5.2What the validator checks

Here's a sample of the checks, with the kind of name that would trigger each.

❌Supply_Air_Temperature_Sensor
Contains uppercase — DBO names must be lowercase.
❌supply-air-temperature-sensor
Contains hyphens — use underscores instead.
❌supply air temperature sensor
Contains spaces — use underscores.
❌supply__air_temperature_sensor
Contains double underscore.
❌_supply_air_temperature_sensor
Starts with underscore.
❌1_supply_air_temperature_sensor
Starts with a number.
❌supply_air_temperature_reading
Doesn't end with a known point-type suffix (sensor, setpoint, command, status, alarm…).
❌supply_air_temperature_status
Semantic clash: temperature is an analogue measurement — _status is for binary/string points. Try _sensor.
❌supply_supply_air_temperature_sensor
Duplicate subfield: "supply" appears more than once — almost certainly a typo.
✅supply_air_temperature_sensor
All four subfields are valid DBO terms. Clean bill of health.

5.3The analogue-vs-binary check, up close

This is the most common mix-up seen in real project schedules. Design engineers often write supply_air_temperature_status when they mean supply_air_temperature_sensor. Both look plausible. Only one is right.

The difference: _status is for things that can only be on/off, running/stopped, open/closed. Temperature is a number on a continuous scale — it doesn't have "statuses." The tool keeps a short list of known analogue measurements and flags any _status point where one of them appears in the name.

validation rule 
// Analogue point names ending in _status are usually wrong
if(lastSeg==='status'){
 for(var ms=0;ms<segs.length-1;ms++){
  if(ANALOGUE_MEASUREMENTS[segs[ms]]){
   issues.push({
    sev:'error',
    msg:'"'+segs[ms]+'" is an analogue measurement — '
      +'"_status" is for binary/string points. '
      +'Try "_sensor" or "_setpoint" for an analogue value.'
   });
   break;
  }
 }
}
Plain English

Only run this check if the name ends in _status. Other suffixes don't have this problem.

Walk through every other subfield in the name (everything except the final _status).

If any of them is a known analogue measurement — temperature, pressure, humidity, flowrate, etc. — we have a contradiction. Analogue readings don't have statuses.

Raise an error that spells out the problem and suggests the likely fix: probably _sensor or _setpoint.

Stop as soon as one analogue brick is found — no point spamming the same error for the rest.

✨
Why this matters in the field

A _status point gets trended as a binary signal in Grafana or any BMS head-end — flat lines flipping between 0 and 1. If the underlying value is actually 23.4°C, the trend is meaningless. Catching this at naming time saves hours of "why does this graph look like that" on commissioning day.

6.3Suggested mappings, how they're built

For any subtype you open, the tool shows three stacked lists: the Required baseline points, the Optional baseline points, and the Observed Extras (anything seen in project data that wasn't on either baseline). Each required/optional row is marked mapped or missing.

submission flow 
function getCatalogMappings(asset,subtype){
 var rows=getSubtypeRows(asset,subtype),
     names={},
     std=EQ.standards[asset]||{required:[],optional:[]};
 // ... collect every DBO name observed for this subtype ...
 var req=[],opt=[],obs=[],stdSet={};
 std.required.forEach(function(name){
  stdSet[name]=1;
  req.push({name:name,
    status:names[name]?'mapped':'missing'});
 });
 // same for optional; anything left is observed-extra
 return {required:req,optional:opt,observed:obs};
}
Plain English

For the asset you asked about (say, AHU), grab the standard DBO baseline — its required and optional points.

Walk through every point ever seen on this specific subtype in project data. Note each name you've observed.

For each required baseline point: if we've seen it, mark it mapped. If not, mark it missing. Same for optional.

Anything observed that isn't on either baseline goes into the "extras" list — a heads-up that this subtype carries points that aren't yet on the standard.

Hand all three lists back. The UI renders them as three neat columns.

⚠️
Important: these are suggested

The mappings are computed from standards plus what's in the Library. They're a starting point for a formal expert review — not an authoritative "this is the complete point list for an AHU." Treat them the way you'd treat a first-draft schedule from a design engineer: useful, imperfect, to be reviewed.

6.5Metadata is browser-local — read this bit

When you save a manufacturer or model against a subtype, it goes into localStorage — specifically a key called epl10_catalogMeta. That means:

✓

It survives refreshes

Close the tab, re-open the file tomorrow — your edits are still there on that laptop, in that browser.

✗

It isn't shared

Someone else opening the same file on their laptop sees their own (empty) metadata. Two engineers editing metadata will not see each other's work.

🗺️
On the roadmap

A proper shared back-end (so manufacturer data flows between laptops) is on the roadmap. Until then, an interim workaround is exporting metadata as JSON and letting another admin import it. Flag the need to the tool maintainer if you run into it before the back-end lands.

7.3Admin gating — who can do what

The tool uses a browser-local MSI sign-in for admin actions. There's a real (if local) user concept. Admin-only actions are gated by a single helper function — ensureAdmin — used in 11 places across the code.

sync + diff logic 
function ensureAdmin(msg){
 if(isAdmin())return true;
 if(msg)toast(msg);
 showAuthModal();
 return false;
}
Plain English

Before any admin-only action, call this function.

If the user is already signed in as MSI, great — return "yes" and let the action continue.

If not, show a small toast explaining what's needed (e.g. "MSI sign-in required for catalogue edits").

Pop up the sign-in modal and return "no" — the caller aborts.

Gated today: add / edit / delete a point, import CSV or JSON, toggle DBO auto-sync, approve or reject submissions, edit catalogue metadata, manually trigger DBO sync.

Three export paths, all routed through the same 19-column canonical schema so the files round-trip cleanly when re-imported. Filenames all start with a consistent prefix, so Export folders stay sortable.

Scenario · Design engineer

A design engineer on a new project wants to add a point for “zone CO₂ concentration”. They’re not signed in as MSI admin. They know the rough name but not the exact DBO subfields.

What’s the right workflow?

This is the submission flow the tool is built for. The Builder teaches the right vocabulary; live validation catches mistakes while they type; the Submit queue routes the proposal to MSI without them having to know who to email.
Email works but bypasses the workflow the tool is designed to make frictionless — and nothing gets validated.
Add Point is admin-only — the button simply isn’t visible when signed out. The Submit queue is the intended path for non-admins.
The whole point of the tool is to avoid ad-hoc names entering project schedules untested. Always validate via the Builder first.
Scenario · Tender

You’re quoting a new job with 3 AHUs and 12 FCUs. You open the Tender Calculator in Typical mode.

What does "Typical" mean, and why is it the default (not Max)?

The calculator used to return worst-case as "standard" — 83 points/AHU when reality is ~20–30. The Typical/Max toggle with honest labels fixed that.
Not the median — the max on any one project. Subtle but important: median would under-count standard points that every project has.
It's the other way round — Typical is the single-project max, Max is the all-projects union.
Scenario · Delivery

You've finished adding 40 new AHU points. You need to hand them over to the client as part of the project deliverables, plus back them up for your own records.

Which two exports do you do?

Two audiences, two formats. Excel is the "user-friendly handover" format; JSON is the "I can feed this back into the tool later" format.
Both CSV is fine-ish, but Excel is often better for a client handover (multi-sheet with DBO reference), and JSON is stronger for backup because it's fully round-trippable.
Screenshots are un-searchable, un-importable, un-everything. Use the export buttons.
Scenario · Governance

A non-admin colleague on your team asks you why they can’t edit manufacturer metadata in the Catalogue, even though they can see it.

What’s happening, and what do you tell them?

The governance principle: editing the Library (including Catalogue metadata) is admin-only. Non-admin users go via the Submit queue for anything they want added or changed — same as they would for a new point name.
It’s deliberate. Admin-only edit buttons are hidden when signed out — no "you can’t do this" dead-ends.
Cache doesn’t come into it — this is about sign-in state, not caching.
Catalogue editing is the intended place for manufacturer/model metadata — just gated behind admin sign-in.
